Q1: SELECT COUNT(*) FROM FirstTab AS ft

Q2: SELECT COUNT(*) FROM FirstTab AS ft

    Subquery: SELECT id FROM SecondTab WHERE id = 5
    → Returns: (5)
    
    Main query: WHERE ft.id NOT IN (5)
    → Checks: 5 NOT IN (5) = FALSE
    →         6 NOT IN (5) = TRUE
    →         7 NOT IN (5) = TRUE
    →         NULL NOT IN (5) = NULL (NULLs don't match)

Q3: SELECT COUNT(*) FROM FirstTab AS ft 
    WHERE ft.id NOT IN ( SELECT id FROM SecondTab )
    
    Subquery: SELECT id FROM SecondTab
    → Returns: (5, NULL)
    
    Main query: WHERE ft.id NOT IN (5, NULL)
    → When NULL is in the list, NOT IN becomes problematic
    → For any value: x NOT IN (5, NULL) 
      = NOT (x = 5 OR x = NULL)
      = (x != 5) AND (x != NULL)
      = (x != 5) AND UNKNOWN
      = UNKNOWN (never TRUE)
    → No rows match when NULL is in the subquery
    
    PREDICTION: 0


Q4: SELECT COUNT(*) FROM FirstTab AS ft 
    WHERE ft.id NOT IN ( SELECT id FROM SecondTab WHERE id IS NOT NULL )

    → Same as Q2
    → Checks: 5 NOT IN (5) = FALSE
    →         6 NOT IN (5) = TRUE
    →         7 NOT IN (5) = TRUE
    →         NULL NOT IN (5) = NULL
    → Matches: 6, 7
    
    PREDICTION: 2


KEY LEARNING:
=============
The tricky part is Q3! When a subquery returns NULL values,
NOT IN behaves unexpectedly because of three-valued logic (TRUE, FALSE, UNKNOWN).
If the subquery contains NULL, NOT IN will never return TRUE for any value.
